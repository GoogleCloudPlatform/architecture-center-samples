# MCP Toolbox for Databases: Oracle EBS R12.2, PeopleSoft 9.2 & JD Edwards EnterpriseOne 9.2

This repository implements the **Model Context Protocol (MCP) Toolbox for Databases** configurations and production-grade Oracle SQL queries for **Oracle E-Business Suite (EBS) R12.2**, **PeopleSoft 9.2** and **JD Edwards EnterpriseOne 9.2** (on Oracle Database), supporting the *Gemini for Government & Enterprise* plugin suite as specified in [PRD_ Gemini for Oracle EBS & PeopleSoft.md](PRD/PRD_%20Gemini%20for%20Oracle%20EBS%20%26%20PeopleSoft.md).

## 2. Key Technical Standards

### 2.1 Unified `connectionString:` Configuration
Database connection details in `tools.yaml` are specified as a single `connectionString:` attribute rather than separated host, port, and service name fields:
* **EBS Source:**
  ```yaml
  sources:
    ebs-oracle-source:
      kind: oracle
      connectionString: ${DB_CONNECTION_STRING:apps.example.com:1521/EBSDB}
      user: ${DB_USER:apps_ai}
      password: ${DB_PASSWORD:apps_ai}
  ```
* **PeopleSoft Source:**
  ```yaml
  sources:
    ps-oracle-source:
      kind: oracle
      connectionString: ${DB_CONNECTION_STRING:oracle-peoplesoft-hcm.c.gcp-project-id.internal:1521/HR92U054}
      user: ${DB_USER:SYSADM_AI}
      password: ${DB_PASSWORD:SYSADM_AI}
  ```
The build and validation suite asserts that `connectionString` exists and that `host`, `port`, and `service_name` are not present.

### 2.2 Oracle Bind Variables (`:param_name`)
All parameter placeholders strictly follow Oracle named bind variable syntax (`:param_name`), matching the declared names under `parameters:` in `tools.yaml` (no PostgreSQL-style `$1` or MySQL-style `?`).

### 2.3 Single-Bind CTE Architecture for Go Driver Interoperability
The MCP Toolbox binary uses Go's `github.com/sijms/go-ora/v2` driver. When a named bind variable is repeated across multiple predicates (e.g. `(:id IS NULL OR col = :id)`) or across `UNION ALL` branches, `go-ora` miscalculates wire bind offsets and raises `ORA-01008: not all variables bound`.

To permanently prevent this driver bug while preserving Oracle named syntax and index performance, all queries define input parameters once via a Common Table Expression (CTE):
```sql
WITH params AS (
    SELECT 
        :param1 AS param1,
        :param2 AS param2
    FROM dual
)
SELECT ...
FROM params p
JOIN target_table t ON (p.param1 IS NULL OR t.col = p.param1)
```
* Binds each parameter exactly once (1:1) in the wire packet.
* Verified 100% compatible with both Oracle Cost-Based Optimizer (SQLcl `EXPLAIN PLAN`) and the MCP Toolbox Go runtime (`toolbox invoke`).
* **No leading comment.** go-ora decides how to run a statement from its first word, so a statement that starts with a `--` or `/*` comment fails with `ORA-00900: invalid SQL statement`. Put notes above the `-- ----` separator or after the `WITH params` CTE; the sync script rejects a leading comment.
* **Bind order matters.** The Toolbox passes parameter values positionally, and go-ora binds them in order of appearance, not by name. Each file's header must therefore declare its binds in the same order the statement uses them (the order of the `WITH params` CTE). The sync script and the validator reject a mismatch, because it would silently put values in the wrong columns.

### 2.4 Semicolon Formatting
* **`tools.yaml`:** Statements omit trailing semicolons (`;`). Passing a trailing `;` via OCI / Go wire protocol causes `ORA-00933: SQL command not properly ended`.
* **Standalone `.sql` Files:** Standalone files in `ebs/sql/` and `peoplesoft/sql/` retain trailing semicolons for direct execution in SQLcl, SQL*Plus, or CI pipelines.
* **PL/SQL blocks:** When the security wrapper is enabled (2.6), statements are anonymous blocks and keep their terminating `END;`, which PL/SQL requires.

### 2.5 Editing SQL (Analyst Workflow)
> Functional analysts: follow [BUILD.md](BUILD.md) for the full step-by-step guide, pre-push checklist, and local testing.

The `.sql` files are the source of truth for each tool's statement, bind parameters, and skill, and the `.txt` files hold the tool descriptions. `tools.yaml` is generated from them. Each `.sql` file has a header ending at the `-- ----` separator, followed by exactly one statement:
```sql
-- Tool: ebs_list_operating_units
-- Skill: schema_discovery_and_lovs
-- Oracle Bind Variables:
--   :name_pattern (string): Optional search pattern to filter operating units by name.
-- -----------------------------------------------------------------------------
WITH params AS (
    SELECT :name_pattern AS name_pattern FROM dual
)
SELECT hou.organization_id, hou.name AS operating_unit_name
FROM apps.hr_operating_units hou, params p
WHERE (p.name_pattern IS NULL OR UPPER(hou.name) LIKE UPPER(p.name_pattern))
ORDER BY hou.name
FETCH FIRST 50 ROWS ONLY;
```
After editing, merge the changes into `tools.yaml` (all options are listed in [3.6](#36-script-command-line-reference)):
```bash
pip install -r requirements.txt
python3 scripts/sync_sql_to_yaml.py           # merge SQL changes into tools.yaml
python3 scripts/sync_sql_to_yaml.py --check   # report drift only; exits 1 if tools.yaml is stale (CI)
python3 scripts/sync_sql_to_yaml.py --diff    # show what changed per statement
python3 scripts/sync_sql_to_yaml.py --out tools.test1.yaml   # write <system>/tools.test1.yaml instead
```
* To add or change a parameter, declare it in the file header (`--   :name (type): description`, type `string`, `integer`, `float` or `boolean`) **and** bind it once in the `WITH params AS (...)` CTE, in the same order. The script rejects files that use a bind more than once, use an undeclared bind, declare one they never use, or declare binds in a different order from the statement.
* To add a new tool, create `<system>/sql/<tool_name>.sql` with `-- Tool:` and `-- Skill:` header lines, and put the tool description (what it returns and when the agent should use it) in `<system>/sql/<tool_name>.txt`. If there is no `.txt` file (or `-- Description:` header lines), the script asks for the description when run in a terminal and saves your answer to the `.txt` file. Changing `-- Skill:` moves the tool to that toolset.
* To keep a tool in the repo but out of `tools.yaml` (for example, its tables are missing from the connected database), add a line `DISABLED: <reason>` to its `.txt` file. The sync skips it, removes it from `tools.yaml` if present, and reports it as `[disabled]`; delete the line to enable it again.
* Every tool's description lives in its `<tool_name>.txt` file next to the `.sql`; edit it there, not in `tools.yaml`. (A tool without a `.txt` file keeps the description stored in `tools.yaml`.) Deleting a `.sql` file only removes its tool when you run with `--prune`.
* **Test variants:** `--out FILENAME` writes `<system>/FILENAME` instead of `tools.yaml`. The first run seeds it from `tools.yaml`; later runs with the same `--out` update it and keep its own settings (for example `--wrap`). Validate a variant with `python3 scripts/build_and_validate.py --config FILENAME`, and run it with `toolbox --config <system>/FILENAME`. Variant names starting with `tools.`, `tools_` or `tools-` (for example `tools.live.yaml`, `tools_sec.yaml`) are git-ignored, so they are never committed by accident.
* On GitHub this is automatic: the `Sync SQL into tools.yaml` workflow runs on every push, commits the updated `tools.yaml` back to the branch, and fails the run if a `.sql` file breaks the rules above. CI cannot prompt, so a new tool pushed without a `.txt` description fails the run until one is added.

### 2.6 Optional PL/SQL Security Wrapper
For fine-grained access control, each tool's SQL can be run inside an anonymous PL/SQL block that first sets a security context, then opens the query as a cursor and returns it with `DBMS_SQL.RETURN_RESULT`. The block is a per-system template at `<system>/templates/plsql_wrapper.sql` containing the placeholder `<<SQL_SCRIPT_GOES_HERE>>`. Templates are provided for every system:

| System | Template | Security call |
| :--- | :--- | :--- |
| PeopleSoft | `peoplesoft/templates/plsql_wrapper.sql` | `sysadm.xx_ai_security_pkg.init_user_session(:user_id)`: **must be installed by a DBA** from `peoplesoft/install/` (maps the email to an OPRID and calls `ps_security_pkg1.initialize_session`) |
| EBS | `ebs/templates/plsql_wrapper.sql` | `apps.xx_ai_security_pkg.init_user_session(:user_id)`: **must be created in the EBS database** (map the email to the FND user, then `fnd_global.apps_initialize` and MOAC `mo_global.init`) |
| JD Edwards | `jde/templates/plsql_wrapper.sql` | `jde_ai.xx_ai_security_pkg.init_user_session(:user_id)`: **must be installed by a DBA** from `jde/install/` (maps the email to one JDE user through the DBA-owned table `XX_AI_USER_MAP`, else `F00926.AUEMLA` / `F01151` and `F0092`, and refuses unknown, switched-off and ambiguous users). It does **not** filter rows: JDE enforces F00950 row security only in its application server, so reproducing it in the database (for example with VPD policies) is still open. |

**Template format.** A header ending at the `-- ----` separator, then an anonymous PL/SQL block:
```sql
-- Free-text comment lines describing the template.
-- Oracle Bind Variables:
--   :user_id (string): Email of the authenticated user; sets the PeopleSoft security context for the query.
-- Auth: :user_id = google-auth.email
-- -----------------------------------------------------------------------------
DECLARE
    rc SYS_REFCURSOR;
BEGIN
    -- 1. Correctly set the user session context
    sysadm.xx_ai_security_pkg.init_user_session(:user_id);

    -- 2. Open the cursor for the PeopleSoft selection query
    OPEN rc FOR
        <<SQL_SCRIPT_GOES_HERE>>;

    -- 3. Implicitly return the cursor back to the database client driver
    DBMS_SQL.RETURN_RESULT(rc);
END;
```
* The body must start with `DECLARE` or `BEGIN`, and contain `<<SQL_SCRIPT_GOES_HERE>>` exactly once, outside comments and strings. Each tool's SQL (without its trailing `;`) is inserted there, indented to the placeholder's column. That's why the template supplies the `;` after the placeholder.
* Every bind the block uses is declared in the header as `--   :name (type): description` and used exactly once.
* `-- Auth: :bind = <auth-service>.<token-claim>` (optional) makes that bind an authenticated parameter; see below.

**Enabling it:**
```bash
python3 scripts/sync_sql_to_yaml.py --system peoplesoft --wrap      # wrap every PeopleSoft tool
python3 scripts/sync_sql_to_yaml.py --system ebs --wrap             # wrap every EBS tool
python3 scripts/sync_sql_to_yaml.py --system peoplesoft --no-wrap   # back to plain SQL
```
* Only `tools.yaml` changes. The `.sql` files stay plain SQL, runnable in SQLcl.
* The choice is recorded as a `# PL/SQL wrapper:` line in the `tools.yaml` header, and later syncs (including CI) keep it until `--no-wrap`.
* Binds declared in the template header (for example `:user_id`) are added to every wrapped tool's parameters, in statement order. A tool that declares the same bind name is rejected.
* Wrapped statements end in `END;`; the validator allows the trailing semicolon only for PL/SQL blocks.

A wrapped tool in `tools.yaml` looks like this (abbreviated):
```yaml
  ps_list_setids:
    kind: oracle-sql
    source: ps-oracle-source
    description: |-
      Lists valid PeopleSoft SetIDs from PS_SETID_TBL. ...
    parameters:
    - name: user_id
      type: string
      description: Email of the authenticated user; sets the PeopleSoft security context for the query.
      required: true
      authServices:
      - name: google-auth
        field: email
    - name: search_pattern
      type: string
      description: Optional search pattern to filter SetID code or description ...
    statement: |-
      DECLARE
          rc SYS_REFCURSOR;
      BEGIN
          sysadm.xx_ai_security_pkg.init_user_session(:user_id);
          OPEN rc FOR
              WITH params AS (
                  SELECT :search_pattern AS search_pattern FROM dual
              )
              SELECT ...
              FETCH FIRST 50 ROWS ONLY;
          DBMS_SQL.RETURN_RESULT(rc);
      END;
    authRequired:
    - google-auth
```

**Authenticated `:user_id`.** Each template's header line `-- Auth: :user_id = google-auth.email` makes `:user_id` a Toolbox [authenticated parameter](https://github.com/googleapis/mcp-toolbox/blob/main/docs/en/documentation/configuration/authentication/_index.md). MCP Toolbox fills it from the `email` claim of the caller's verified Google ID token, and the agent cannot set it. With `--wrap`, the sync adds `authRequired: [google-auth]` to every tool, plus `required: true` and `authServices: [{name: google-auth, field: email}]` to the `user_id` parameter.

The auth service itself is environment config. Like `sources:`, it is maintained by hand, and the sync preserves it. Each `tools.yaml` ships with the block **commented out** in its header (the only place the sync keeps comments):
```yaml
# authServices:
#   google-auth:
#     type: google
#     clientId: ${GOOGLE_CLIENT_ID}
```
**Two secured variants, generated for you.** `python3 scripts/build_and_validate.py` writes both for every system: `<system>/tools_agent.yaml` (`--wrap --identity agent`: `user_id` is a plain parameter, no `authServices`) and then `<system>/tools_sec.yaml` (seeded from it, `--identity token`: the Toolbox verifies the Google token; its `google-auth` service is defined automatically as `clientId: ${GOOGLE_CLIENT_ID}`). Both are git-ignored. Deploy them with `deploy_mcp_server.sh --variant agent` and `--variant sec` (section 3.7); `tools.yaml` itself keeps the hand-maintained, commented-out `authServices` block described below.

Before the first `--wrap`, uncomment it by removing the leading `# ` (the sync refuses to wrap until it exists). Then set the OAuth client ID your agent's tokens are issued for in your `.env` file: `GOOGLE_CLIENT_ID`.

Wrapped tools can't be run with `toolbox invoke` (or `scripts/test_live_toolbox.py`), because it cannot send the token. Start the server with the HTTP API and pass a Google ID token for the configured client ID in the `google-auth_token` header.

**Testing locally with your gcloud login.** `gcloud auth print-identity-token` issues tokens whose audience is gcloud's own public OAuth client, `32555940559.apps.googleusercontent.com`. Point a git-ignored test variant at that client ID and your own login becomes the authenticated user, without touching `tools.yaml` (shown for PeopleSoft; use `ebs` and `EBS_*` for EBS):
```bash
# 1. Build a test variant and add the auth service to it (the admin step)
python3 scripts/sync_sql_to_yaml.py --system peoplesoft --out tools.live.yaml
#    then uncomment the authServices block at the top of peoplesoft/tools.live.yaml
python3 scripts/sync_sql_to_yaml.py --system peoplesoft --out tools.live.yaml --wrap

# 2. Start the server (database credentials from peoplesoft/.env.database; VPN/tunnel up)
eval "$(./scripts/env_export.sh --system peoplesoft)"
export GOOGLE_CLIENT_ID=32555940559.apps.googleusercontent.com   # gcloud's client ID: local testing only
toolbox --config peoplesoft/tools.live.yaml --enable-api -p 5001

# 3. In another terminal: call a tool as yourself
ID_TOKEN=$(gcloud auth print-identity-token)    # valid for 1 hour
curl -s -X POST http://127.0.0.1:5001/api/tool/ps_list_setids/invoke \
     -H "Content-Type: application/json" -H "google-auth_token: $ID_TOKEN" \
     -d '{"search_pattern": ""}'
```
Expected results:
* Without the header, you get HTTP 401 `tool invocation not authorized`.
* With it, the rows are returned for the security context of your Google email.
* A `user_id` placed in the request body is ignored: authenticated parameters come only from the token.

Production must use the real OAuth client ID that your agent's tokens are issued for, never gcloud's.

### 3.2 Installing MCP Toolbox for Databases (`toolbox`)

The MCP Toolbox for Databases is Google's open-source server for exposing databases to AI agents via the Model Context Protocol.

#### macOS (via Homebrew)
```bash

```

#### Linux (Direct Binary)
Download the precompiled binary (URLs are listed in the [release notes](https://github.com/googleapis/mcp-toolbox/releases)):

```bash
curl -Lo toolbox https://storage.googleapis.com/mcp-toolbox-for-databases/v1.13.1/linux/amd64/toolbox

```

```bash
go install github.com/googleapis/mcp-toolbox@latest

```

```bash
toolbox --version
```

### 3.3 Database Connection & Environment Configuration

Each `tools.yaml` file reads database credentials dynamically from environment variables, falling back to development defaults if unset.

Set the credentials for your environment before launching the server. The same per-system files serve local runs and Cloud Run deploys (section 3.7). Create them once, fill in `<system>/.env.database` (git-ignored, mode 600), and load them into your shell:
```bash
./scripts/deploy_mcp_server.sh --system ebs --init-env     # creates ebs/.env and ebs/.env.database
$EDITOR ebs/.env.database                                   # DB_CONNECTION_STRING, DB_USER, DB_PASSWORD
eval "$(./scripts/env_export.sh --system ebs)"              # export them (also GOOGLE_CLIENT_ID from ebs/.env)
```
`env_export.sh` takes `--system ebs|peoplesoft|jde`. It reads the values literally, so passwords with `$`, `#` or spaces work, and it skips empty values. For JD Edwards, uncomment `JDE_DATA_SCHEMA` and `JDE_CTL_SCHEMA` in `jde/.env.database` if your schemas are not `PRODDTA`/`PRODCTL`. A leftover root `ebs.env` (the old layout) is still sourced when `<system>/.env.database` is missing, with a warning.

Or export the variables directly:

#### Oracle E-Business Suite (EBS)
```bash
export DB_CONNECTION_STRING="apps.example.com:1521/EBSDB"
export DB_USER="apps_ai"
export DB_PASSWORD="your_ebs_password"
```

#### PeopleSoft 9.2
```bash
export DB_CONNECTION_STRING="oracle-peoplesoft-hcm.c.gcp-project-id.internal:1521/HR92U054"
export DB_USER="SYSADM_AI"
export DB_PASSWORD="your_ps_password"
```

#### JD Edwards EnterpriseOne 9.2
```bash
export DB_CONNECTION_STRING="jde.example.com:1521/JDEPROD"
export DB_USER="JDE_AI"
export DB_PASSWORD="your_jde_password"
```
The JDE user needs `SELECT` on the `PRODDTA` (business data) and `PRODCTL` (control tables) tables the tools read. For another path code, change the schema prefixes in `jde/sql/*.sql` (e.g. `CRPDTA`/`CRPCTL`).

#### Google OAuth client ID (only with the PL/SQL security wrapper, section 2.6)
```bash
export GOOGLE_CLIENT_ID="1234567890-abc.apps.googleusercontent.com"
```

### 3.4 Running the MCP Toolbox Server

You can run the toolkit locally in three different modes depending on your workflow:

#### Mode 1: HTTP / SSE Server with Interactive Web UI (Recommended for Testing)
Start the server with the `--ui` flag to open an interactive web console where you can inspect tool schemas, test parameters, and view live database responses:

* **For Oracle EBS (listening on port 5000):**
  ```bash
  toolbox --config ebs/tools.yaml --ui -p 5000
  ```
  Open `http://localhost:5000` in your browser. The MCP endpoint will be served at `http://localhost:5000/mcp`.

* **For PeopleSoft 9.2 (listening on port 5001):**
  ```bash
  toolbox --config peoplesoft/tools.yaml --ui -p 5001
  ```
  Open `http://localhost:5001` in your browser.

> [!NOTE]
> Because the systems share standardized skill/group names (e.g. `policy_and_statute_assistant`), run each system (EBS, PeopleSoft, JD Edwards) as a separate server instance or port to avoid group name collisions.

#### Mode 2: STDIO Mode for AI Desktop and IDE Clients (Cursor, Gemini CLI, Antigravity)
To connect the MCP server directly to an assistant, configure the client's MCP configuration JSON:

* **MCP Client Configuration** (e.g. `mcp_config.json`):
  ```json
  {
    "mcpServers": {
      "oracle-ebs": {
        "command": "toolbox",
        "args": ["--config", "/absolute/path/to/oracle-mcp-1p/ebs/tools.yaml", "--stdio"],
        "env": {
          "DB_CONNECTION_STRING": "apps.example.com:1521/EBSDB",
          "DB_USER": "apps_ai",
          "DB_PASSWORD": "your_ebs_password"
        }
      },
      "oracle-peoplesoft": {
        "command": "toolbox",
  ```

### 3.6 Script Command-Line Reference

#### `scripts/sync_sql_to_yaml.py`: merge `.sql`/`.txt` files into `tools.yaml`
| Option | Effect |
| :--- | :--- |
| *(none)* | Merge changes for every system into `ebs/tools.yaml`, `peoplesoft/tools.yaml` and `jde/tools.yaml`. |
| `--system {ebs,peoplesoft,jde}` | Limit to one system. Repeatable. |
| `--check` | Report drift without writing anything; exit 1 if any file is out of date (for CI). |
| `--diff` | Also print a unified diff of every changed statement. |
| `--prune` | Remove tools whose `.sql` file has been deleted. Without it they are only reported. |
| `--no-input` | Never prompt for a new tool's description. A new tool without a `.txt` file is then an error (for CI). |
| `--out FILENAME` | Write `<system>/FILENAME` instead of `tools.yaml`. The name must end in `.yaml`/`.yml` and contain no directory. The first run seeds it from `tools.yaml`, and later runs update only that file. |
| `--seed-from FILENAME` | With `--out`: seed a new file from `<system>/FILENAME` instead of `tools.yaml`. |
| `--wrap` | Enable the PL/SQL security wrapper from `<system>/templates/plsql_wrapper.sql` (2.6). Remembered in the file's header. |
| `--no-wrap` | Disable the wrapper. Remembered in the file's header. |
| `--identity {token,agent}` | With `--wrap`: who supplies `user_id`. `token` (default): the Toolbox verifies the caller's Google token (`authServices` and `authRequired`). `agent`: a plain required parameter that the calling agent fills with an identity it verified itself; the file must then be deployed only behind a private service that only that agent can invoke. Remembered in the header (`# Identity:`). |

Exit codes:
* **0:** in sync, or updated.
* **1:** drift found with `--check`.
* **2:** a `.sql`, `.txt` or template file failed validation, or an option is invalid. Nothing is written.

#### `scripts/build_and_validate.py`: generate the secured variants and validate the configs
Each run first regenerates, for every system, the two variants you deploy as MCP servers, then validates `tools.yaml` and both:

1. `<system>/tools_agent.yaml`: `tools.yaml` wrapped in the PL/SQL security block, with `user_id` a plain required parameter and no `authServices` (`sync_sql_to_yaml.py --out tools_agent.yaml --wrap --identity agent`). It is for a Toolbox that only the agent can invoke, where the agent fills `user_id` with the email it verified. Deploy it with `deploy_mcp_server.sh --variant agent`.
2. `<system>/tools_sec.yaml`: seeded from `tools_agent.yaml`, wrapped, with `user_id` filled by the Toolbox from the caller's verified Google token (`--identity token`: `authServices` and `authRequired`, with the `google-auth` service defined as `clientId: ${GOOGLE_CLIENT_ID}`). Deploy it with `deploy_mcp_server.sh --variant sec`.

Both are git-ignored like every `tools_*.yaml`. `--no-generate` skips this step.
| Option | Effect |
| :--- | :--- |
| *(none)* | Generate the variants, then validate every system's `tools.yaml`, `tools_agent.yaml` and `tools_sec.yaml`: in sync with the SQL files, connection settings, bind usage and order, semicolons and `END;`, toolset membership, and `authServices` references. |
| `--system {ebs,peoplesoft,jde}` | Limit to one system. Repeatable. |
| `--config FILENAME` | Validate only `<system>/FILENAME`, for example a `--out` variant; generates nothing. |
| `--no-generate` | Do not regenerate `tools_agent.yaml` and `tools_sec.yaml`. |
| `--compile-variants` | Also compile the generated variants. Their wrapper calls a security package (for example `apps.xx_ai_security_pkg`) that must already exist in the database, so by default only `tools.yaml` is compiled. |
| `--compile` *(default)* | Also connect to each system's database and parse every statement exactly as written in `tools.yaml` (wrapper included), so SQL that would fail on the MCP server (missing table or column, bad syntax, missing package) is caught before it is pushed. Nothing is executed. Needs python-oracledb (`pip install -r requirements.txt`) and a reachable database; connection per system: `<SYSTEM>_DB_USER`/`_DB_PASSWORD`/`_DB_CONNECTION_STRING` variables, else (JDE) the running stub database, else `<system>/.env.database`. |
| `--nocompile` | Skip the database check, for CI or a laptop without the tunnel. A system whose database cannot be reached fails unless this is given. |

If python-oracledb cannot log in (the EBS `apps_ai` password has an old verifier that thin mode rejects, DPY-3015) or is not installed, the same checks run through SQLcl (`sql` on `PATH`) instead. `${VAR:default}` placeholders in statements (the JDE schema names) are expanded from the environment, `<system>/.env` and `<system>/.env.database` first, as the Toolbox does.

For a PL/SQL wrapper block Oracle compiles only on execution, so the check parses the `OPEN ... FOR` query inside it and verifies that each called `schema.package.procedure` exists in the database; other contents of the block are not compiled.

Exit codes: **0** if everything is valid; **1** if any check fails (each failure is listed).

#### `scripts/test_live_ebs.py` and `scripts/test_live_toolbox.py`: live EBS tests
Neither script takes options. Both use the `DB_*` variables, so run `eval "$(./scripts/env_export.sh --system ebs)"` first.
* **`test_live_ebs.py`** runs `EXPLAIN PLAN` in SQLcl (`sql` on `PATH`) for every `ebs/sql/*.sql`. Exit 1 if any fail; exit 2 if a `.sql` file fails parsing.
* **`test_live_toolbox.py`** calls every tool in `ebs/tools.yaml` through `toolbox invoke`, with sample parameters from its `SAMPLE_INVOCATION_PAYLOADS` table. Exit 1 if any fail. It stops with exit 2 when the tools require an auth token (wrapped config), because `toolbox invoke` cannot send one.

The first run pulls the image (about 1 GB, no login) and takes a minute or two. Each run drops and rebuilds the `PRODDTA` / `PRODCTL` schemas from `jde/stub/schema.sql` and `jde/stub/seed.sql`, then runs every `jde/sql/*.sql` as a read-only `JDE_AI` user and checks the row count and key values against the seed scenario.
| Option | Effect |
| :--- | :--- |
| *(none)* | Run each tool's statement directly. |
| `--toolbox` | Also run each tool through `toolbox invoke` with `jde/tools.yaml` (go-ora, positional binds). Skipped when that file is wrapped. |

### 3.7 Deploying to Cloud Run (`scripts/deploy_mcp_server.sh`)

One command deploys one system's Toolbox to a private Cloud Run service. `--system {ebs|peoplesoft|jde}` is required (`ps` is an alias of `peoplesoft`) and drives everything: the env files, the service name (`mcp-toolbox-<ebs|ps|jde>`, plus `-<variant>` with `--variant`), the runtime service account (`<ebs|ps|jde>-service-account`), the secrets and the tools file (`<system>/tools.yaml`, or `<system>/tools_<variant>.yaml`). Deployments of different systems never share state.

```bash
./scripts/deploy_mcp_server.sh --system ebs --init-env   # 1. create ebs/.env and ebs/.env.database from the templates
$EDITOR ebs/.env.database                                 # 2. DB_CONNECTION_STRING, DB_USER, DB_PASSWORD (optional, see below)
./scripts/deploy_mcp_server.sh --system ebs --check      # 3. fill blank settings and verify GCP; deploys nothing
./scripts/deploy_mcp_server.sh --system ebs              # 4. deploy
```

**Files** (git-ignored, mode 600; the templates stay at the repo root):

| File | Holds | Created from |
|---|---|---|
| `<system>/.env` | Deploy settings: project, region, service account, network, subnet, bucket, service name, image, tools file, `GOOGLE_CLIENT_ID`, service URL | `.env.example` |
| `<system>/.env.database` | `DB_CONNECTION_STRING`, `DB_USER`, `DB_PASSWORD` (any other `${VAR}` that `tools.yaml` references works too) | `.env.example.database` |

`--init-env` replaces the `{{SYSTEM}}`, `{{SYSTEM_SHORT}}` and `{{SYSTEM_UPPER}}` placeholders in the templates. It asks before overwriting and keeps a timestamped `.bak` copy of any file it replaces. A legacy `.env.<system>` in the repo root is moved to `<system>/.env` (after confirmation) on the next run. Values are written in double quotes.

**Where each value comes from**
* **Settings** (`<system>/.env`): command-line option, then the file, then a derived default. `--check` detects blank values and proposes one (the active gcloud project, an existing service account, discovered networks, subnets and buckets, the `<system>/tools*.yaml` files, client IDs from `scripts/secrets/<system>*.json`). The value you accept or type is written back to the file.
* **Database credentials:** the process environment, then `<system>/.env.database`, then a hidden prompt. They go to Secret Manager over stdin, one secret per variable (`<service-name>-db-user` and so on), and Cloud Run reads them at startup. They are never on a command line or on screen. A filled-in `.env.database` is what makes an unattended deploy possible. Values are read literally, so a password may contain `$`, `#` or spaces.

**Variants.** To keep several deployments of one system (for example a `sec` Toolbox that verifies the Google token and an `agent` Toolbox for the agent, section 2.6; their default tools files are `<system>/tools_sec.yaml` and `<system>/tools_agent.yaml`), add `--variant NAME` to every command. The variant gets its own `<system>/.env.<NAME>` (create it with `--system peoplesoft --variant agent --init-env`), service name `mcp-toolbox-<ebs|ps|jde>-<NAME>` and secrets, so the variants never touch each other. Database credentials come from `<system>/.env.<NAME>.database` if it exists, otherwise from the shared `<system>/.env.database`. `--variant` takes lowercase letters, digits and single hyphens. An existing `<system>/.env` keeps working as the "no variant" deployment; rename it to `.env.<NAME>` to adopt a variant.

**Prompts.** At a proposal, Enter accepts, `n` skips and typing a value uses it. In a numbered list, Enter picks 1, `n` skips and typing a value uses it. Choices that are not already in `<system>/.env` or on the command line (subnet, bucket, tools file, client ID) are asked even with `--yes`; `--yes` only auto-answers the yes/no confirmations (create, upload, grant, deploy). Without a terminal the script cannot ask, so it stops and names the setting to provide.

**Useful options:** `--check` (settings and GCP verification only), `--fix` (enable missing APIs, create the service account, grant roles), `--dry-run`, `--status`, `--tools-file PATH`, and `--project`, `--region`, `--network`, `--subnet`, `--bucket`. `--help` lists them all. After deploying, the script offers to record the service URL as `MCP_SERVER_SQL_URL` in the env file; verify the service with `scripts/test_mcp_server.sh`.

**Rotating.** Both rotations compare with what is already there before changing anything.
* `--rotate-secrets` adds a new version of each database secret. The new value (environment, `.env.database` or prompt) is compared by SHA-256 hash with the latest version, and nothing is printed. An identical value gets a warning and no new version; a difference of only a trailing newline is called out (a stray newline is a classic cause of `ORA-01017`).
* `--rotate-tools` only replaces `gs://<bucket>/<service>/tools.yaml` with the local `--tools-file`, after confirmation, with no deploy or preflight. If the bucket already holds the identical file it warns and replaces nothing.
* **Restart.** The Toolbox reads its config and secrets when an instance starts. After an actual rotation the service is restarted by starting a new revision (`TOOLBOX_RESTART_AT` env var) and a `restart-reason` annotation records why and when (`tools rotated 2026-10-09T14:12:13Z`); a service annotation alone would not start a revision. `--rotate-tools` asks first, `--rotate-secrets` restarts only when the deploy left the old revision running, and `--no-restart` skips it.

**With the PL/SQL wrapper** (section 2.6): the tools file must have its `authServices` block enabled and `GOOGLE_CLIENT_ID` set in `<system>/.env`, or the preflight fails. The sync strips system prefixes from variable names (`${PS_DB_USER}` becomes `${DB_USER}`), so the same names work for every system.

### JD Edwards EnterpriseOne 9.2 Tools (18 Tools)

**Schema names are configurable.** The SQL files say `proddta.` and `prodctl.`; `tools.yaml` reads them as `${JDE_DATA_SCHEMA:proddta}` and `${JDE_CTL_SCHEMA:prodctl}`, so a database with other names (for example `PS920DTA`/`PS920CTL` or `TESTDTA`/`TESTCTL`) needs only `JDE_DATA_SCHEMA="..."` and `JDE_CTL_SCHEMA="..."` in `jde/.env.database` (see `.env.example.database`), with no change to the SQL. Do not export them empty.

JDE conventions the SQL handles: dates are Julian `CYYDDD` numbers (returned as `YYYY-MM-DD`), amounts are stored without the decimal point (divided by 100, unit costs by 10,000), codes are blank-padded fixed-length strings, and Unicode databases use `NCHAR` columns.

## 5. Verification and Testing

### 5.1 Automated Sync and Schema Validation
Checks that `tools.yaml` is in sync with the `.sql` files, and asserts that parameter definitions, connection strings, and syntax rules match. The `Sync SQL into tools.yaml` GitHub Action runs the sync and this validator on every push:
```bash
python3 scripts/build_and_validate.py
```
*Outputs: `18 tools across 7 toolsets validated` for PeopleSoft and JDE (`24 tools` for EBS), then `[SUCCESS] All configurations validated.`*

### 5.2 Live Database EXPLAIN PLAN (SQLcl)
Validates query syntax, Oracle data dictionary synonyms, table joins, and column names against the live Oracle EBS 19c database:
```bash
python3 scripts/test_live_ebs.py
```
*Outputs: 24 passed, 0 failed out of 24 tools.*

### 5.3 End-to-End Live MCP Toolbox Execution
Invokes all 24 EBS tools through the `toolbox` CLI binary against the live Oracle EBS database instance (unwrapped configs only; see 3.6):
```bash
python3 scripts/test_live_toolbox.py
```
*Outputs: 24 passed, 0 failed out of 24 tools.*

### 5.4 JD Edwards Stub Database Tests
No live JD Edwards database is available yet, so the live test scripts cover EBS only. `scripts/test_stub_jde.py` runs the 18 JDE tools against stub `PRODDTA`/`PRODCTL` tables (column names, types and lengths from the JDE 9.2 data dictionary, `NCHAR` for strings as in a Unicode JDE database) in a local Oracle Database Free container: directly, through `toolbox invoke` (go-ora), and inside the PL/SQL wrapper (see 3.6):
```bash
python3 scripts/test_stub_jde.py --toolbox --wrap
```
*Outputs: `[PASS]` for each of the 18 tools in each mode, then `[SUCCESS] All checks passed.`* Before production use, run them against a real JDE database to confirm.

### 5.5 Manual Tool Execution via Toolbox CLI
You can invoke any individual tool directly from the terminal:
```bash
toolbox invoke ebs_list_operating_units '{"name_pattern": "%Vision%"}' --config ebs/tools.yaml
```
