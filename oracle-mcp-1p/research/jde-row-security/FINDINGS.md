Every database change made is in [DB_CHANGELOG.md](DB_CHANGELOG.md); the prototype is in [lab/](lab/).

## 1. Summary

1. JDE "row security" restricts which **rows** a user can see or change, by ranges of a data item (business unit, company, address number...). It is set in Security Workbench (P00950), stored in `SY920.F00950` and enforced **by the JDE application server**, which adds the predicate to the SQL it sends `[doc]`. The database does not know about it, so any direct SQL (our Toolbox) bypasses it.
2. In this database there is **no row security at all** `[db]`: `F00950` has 20 rows, none of type 4 (row security): 18 type `9`, one `B`, one `S`. No VPD policies exist on the JDE schemas (the 12 other policies in the database are Oracle's own). So the demo data cannot tell us what real rules look like; an expert (or a sample export from a real site) is needed (Q1, Q2).
3. A database-side reproduction is feasible: a prototype with a package that resolves the JDE user, reads type-4 rows, and returns a VPD predicate passes 13 behaviour checks `[lab]`. But the checks only prove my reading of the documentation, not that JDE behaves that way. The open questions below decide whether the design is right.
4. **The identity step is the weak link today:** all 5 users that have an address book number share `ULAN8 = 1`, and `AN8 1` has no e-mail row `[db]`, so e-mail login cannot resolve anyone in this database.

## 2. How JDE row security works `[doc]`

- Configured per **user, role or `*PUBLIC`**. The system looks at the user first, then the user's roles, then `*PUBLIC`; the first level that has row security wins and lower levels are ignored.
- A rule = **table** (or `*ALL`) + **data item (alias)** + **from value** + **thru value** + flags **View / Add / Change / Delete** (Y/N).
- Set on **tables**, not business views. Securing an alias on a table that does not contain it has no effect and no error.
- The data item must have **Row Security** switched on in the data dictionary (P92001). Stored in `DD920.F9210.FRSCFG = 'Y'` `[db]`: 538 aliases here (the 9.2 docs say 504), including `MCU`, `CO`, `AN8`.
- Two **modes**, chosen once for the whole system, never mixed:
  - **Exclusive** (default): listed ranges with `N` are hidden, everything else is visible. SQL: `ABMCU NOT BETWEEN ' 21' AND ' 50' AND ...`.
  - **Inclusive** (recommended by GSI and Quest): only listed ranges with `Y` are visible. SQL: `(ABMCU BETWEEN ' 1' AND ' 20' OR ...)`. If a user has rules but none with `Y` for an operation, that operation is blocked on the table.
- Enforcement SQL for SELECT uses View, for UPDATE uses Change, etc. Our tools are read-only, so only **View** matters for us.
- Warnings from Oracle: use sparingly, it costs performance; do not change mode once type-4 records exist `[doc]` (Quest).
- Intercompany exception: "Exclusive Application security" can exempt a program or UBE from row security `[doc]` (GSI).

## 5. Design observations (not decisions)

- **VPD is the natural fit** for a read-only Toolbox: the tool SQL does not change and joins are filtered per table. But policies would sit on the **real** `PRODDTA` tables that the E1 application also uses, and the policy would have to be bypassed for the JDE application's own database user (`EXEMPT ACCESS POLICY` or a policy that checks the session user). That needs a DBA and a site decision.
- **`*ALL` rules** apply to every table that contains the alias: one policy per such table, generated from the table specs, not hand-written. Unknown how many tables that is (Q5).
- **Connection pooling:** the identity is stored in the database session. If the Toolbox reuses a connection and a call skips the wrapper, the previous caller's identity would still be there. The wrapper is the first statement of each tool call so this is covered today, but the package should also clear the identity at the end of each call (not yet in the lab).
- **Alternative that avoids all this:** read through JDE itself (AIS / Orchestrator REST), which enforces security natively. Costs: different tools, slower, needs a JDE server and credentials. Worth asking the customer (Q13).
- **The current `xx_ai_security_pkg` does not filter rows.** The README already says so; this research does not change that, it only sizes the work.

| Q1 | **Type `4` is row security** (Oracle admin guide pages plus GSI and Quest both say "Type 4"). Type `5` is processing option / data selection security (Oracle). **`9`, `B`, `S` rows here:** they are not row security. The 18 type-`9` rows have the library/schema name as user (`PRODDTA`, `TESTDTA`...), object `R98405A` and `FSRUN='Y'`; the `S` row is `*PUBLIC` / `*ALL` with `FSRUN='Y'`. | Q2 | **Column mapping** as used in the lab is right in intent: `FSOBNM` = table (or `*ALL`), `FSDTAI` = data item alias (`MCU`, `CO`, `AN8`), `FSFRDV` / `FSTHDV` = from / thru value, `FSVWYN` = View, `FSA` = Add, `FSCHNG` = Change, `FSDLT` = Delete. It is still **inference, not a sample**: we still need a few real type-4 rows. | **Medium** |
| Q3 | **The mode flag is a record in `F00950` with `FSUSER = 'EXCLUSIVE'`** (Oracle's activation page for releases before 8.9 inserts exactly that record, `FSATN3='1'`; since 8.9 it is set in P00950 under *Form > Exclusive/Inclusive*). **This database has no such record** `[db]` (0 rows with `FSUSER` = `EXCLUSIVE`/`INCLUSIVE`), so it is in the **default: exclusive**. The `B` row is not the flag. **Design rule:** read the flag; no flag record means exclusive. | Q4 | **Values are compared as the column's stored format.** Business unit (`MCU`) is a 12-character, right-justified string, so a range `1` to `99` is a *string* range that also catches `AA` (Quest: read it as blank-to-99); Oracle's generated SQL shows `' 21'` for exactly that reason. Numeric aliases (`AN8`) compare as numbers. Company (`CO`) is a 5-character string and **blank is a valid value**, `00000` has a special financial use (Quest). A blank thru value most likely means "same as from" (Oracle lists Thru as optional): untested. Special values `*ALL`/`*BLANKS` appear in GSI's advice (ALL-to-ALL and `*BLANKS`-to-`*BLANKS` ranges for MCU to avoid problems in `F41001`/`F41002`), so the policy must treat blank data as a real value. Blank thru, `*BLANKS`: **Low** |
| Q5 | **Yes, the table spec is the source, and it is complete.** `PS920.F98711` lists table / data item / SQL column (`TDOBNM`, `TDOBND`, `TDSQLC`) `[db]`: `F0101`: `MCU` to `ABMCU`, `AN8` to `ABAN8`; `F0006`: `MCU` to `MCMCU`. | Q6 | **Roles:** `F95921` is the user-to-role and role-to-role relationship table: `RLFRROLE` is the member (user or role), `RLTOROLE` the role it belongs to; `RLEFFDATE`/`RLEXPIRDATE` bound validity, so the policy must ignore expired relationships (the lab does not yet). **Several roles:** inclusive merges naturally (a user sees the **union** of the roles' ranges); merging **exclusive** sets is the dangerous case (Quest: two sets of exclusions can leave a user with nothing). **Which level wins:** Oracle's wording is "if you set security at a higher level, lower levels are ignored", which I read as **per user, not per table or alias** (so one user-level rule for any alias hides *all* role and `*PUBLIC` rules). Union in inclusive: **Medium**. Winner granularity: **Low** |
| Q7 | **An alias with no rules at the user's effective level is unrestricted; an alias that has rules but no matching range hides the row.** This is how I read Oracle ("a record with all N for the operation disallows it") together with GSI's advice to add ALL-to-ALL and `*BLANKS` ranges: those advice items only make sense because rows outside every listed range disappear in inclusive mode. So row security is **per secured data item**, not "no rules = no access". This matches what the lab does (no rules = unrestricted, rules without `View=Y` = nothing). It is **fail-open for users nobody configured**. **Recommendation (a design choice, not a JDE fact):** make it a switch. For a government customer I would ship strict as the recommended setting and document the difference. | JDE behaviour: **Medium**. Recommendation: judgement |

| Q11 | **Recommended architecture: VPD on only the tables the tools read, written so it applies only to the Toolbox's database user.** The policy function returns `NULL` (no filter) unless the session user is the Toolbox user (`JDE_AI_RO` here), so the JDE application and every other user are completely unaffected; and for the Toolbox user it fails closed when no identity is set (already in the lab). | Q12 | **Oracle says set row security on tables, not business views**, and "securing an item on a table that lacks it has no effect and no error". The JDE database layer builds the predicate **for each table in the statement it generates**, so joined tables are each filtered; a secured table joined to an unsecured one filters only the secured side. VPD does exactly this per table, so it matches, **provided each joined table that has a secured alias gets a policy** (hence Q5's generator). A tool joining `F0101` to `F0006` would be filtered on both if both have `MCU` rules. | Oracle statement: **High**. Join behaviour: **Medium** |
| Q13 | **AIS REST is a valid, strategic option for a few high-value data sets**: calls run as the real JDE user, so row, column, application and action security (and address book privacy) apply by definition. I would **not** replace the SQL tools; I would offer it as phase 2 for any data set where the customer refuses DB-level enforcement. This is a customer question, not a technical blocker. | **Medium** (opinion) |
| Q14 | **No hard numbers anywhere; Oracle only says "use sparingly".** Quest calls the impact minor but real; GSI says inclusive produces simpler, faster SQL (a few `BETWEEN`s instead of many `NOT BETWEEN`s). ### What this changes in the design

1. Filter on `FSSETY='4'`; read the mode from the `FSUSER='EXCLUSIVE'` flag record (absent = exclusive); do not copy anything else from `F00950`.
2. Take table, alias to column from `F98711`, and width/type from the table spec, never hard-coded (the lab hard-codes 12 characters).
3. Honour `F95921` effective and expiry dates; treat multiple roles as a union in inclusive mode; decide the exclusive-mode merge rule with the customer.
4. Policy returns `NULL` for any session user other than the Toolbox user; fails closed for the Toolbox user with no identity.
5. Add a strict switch for "user has no row-security rule at all" (Q7).
6. Identity: move to `F00926.AUEMLA` then `F01151`, or a DBA-owned mapping table (Q9). This is still the first blocker.
7. Still unverified and **worth one hour with a human analyst or a test JDE**: Q2 (a real type-4 export), Q3 (toggle inclusive and diff `F00950`), Q6 (winner granularity), Q4 (blank thru).
